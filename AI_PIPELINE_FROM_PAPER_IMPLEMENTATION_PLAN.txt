1. Short Review of the Paper
----------------------------

The paper recommends a modular, sensor-first, multi-model architecture instead of one large monolithic AI model.

The important idea is:

1. Collect streaming telemetry from sensors.
2. Check signal quality and missing values.
3. Convert raw sensor packets into model features.
4. Use a prediction model to estimate:
   - impact detection
   - impact zone
   - severity
   - vital sign risk
   - time-to-emergency / deterioration risk
5. Use a separate intervention policy module to choose safe recommendations.
6. Show uncertainty/confidence and allow the system to abstain when data is bad.
7. Log outcomes, recommendations, and user responses for future model improvement.

The paper's best recommendation for this project:
- Do not start with a huge LLM or vision-language model.
- Start with time-series sensor data + patient profile data.
- Use hybrid fusion:
  - early fusion for aligned sensor streams like ECG, piezo, MAX30102, IMU
  - late fusion for patient profile, GPS, optional future text/audio/image
- Keep recommendation generation separate from prediction.

PHASE 2 - Signal Quality Layer

Goal:
Before prediction, decide if each sensor is reliable.

Quality checks:

ECG:
- leadOff must be false
- ecg must not be stuck at 0 or 4095
- ecgWave must have real variation

MAX30102:
- fingerDetected should be true
- IR should be above contact threshold
- SpO2 should be between realistic bounds

Piezo:
- piezoDelta should not be permanently zero
- piezoRaw should not be permanently 0 or 4095
- GPIO36/GPIO39 may float if no pulldown, so mark them lower confidence if unstable

MPU:
- accelMagnitude should not be impossible
- gyroMagnitude should be finite

Output:

quality: {
  ecgOk: true,
  max30102Ok: true,
  piezoOk: true,
  motionOk: true,
  missingSensors: [],
  warnings: []
}

Files to change:
- server/index.js
- src/MODELE_IA.js

Possible new file:
- src/ai/signalQuality.js

PHASE 8 - Policy and Recommendation Module

Goal:
Separate prediction from recommendation.

Do not let a chatbot invent medical advice.
Use a structured action policy.

Action schema:

{
  actionType: "monitor" | "check_sensor" | "check_bleeding" | "immobilize" | "chest_assessment" | "evacuate",
  targetOutcome: "reduce_risk",
  urgency: "low" | "medium" | "high" | "critical",
  messageTemplateId: "impact_limb_01",
  contraindications: [],
  humanEscalationRequired: true,
  confidenceRequired: 70
}

Recommendation output:

{
  allowed: true,
  actionType: "check_bleeding",
  urgency: "high",
  message: "Impact detected on right leg. Check bleeding and monitor SpO2/cardio.",
  reason: "Piezo right leg high + heart rise",
  requiresHumanReview: true
}

Files to add:

8. What Not To Do First
-----------------------

Do not start with:
- Llama
- Qwen-VL
- big LLM chatbot
- vision-language model
- cloud-only heavy model

Why:
- Your current project has sensor time-series data, not camera/text/audio input.
- You first need labels and logged data.
- A simple explainable model is better for competition/demo and debugging.


9. Final Recommended First Implementation
-----------------------------------------

The best next implementation is:

1. Add telemetry logging in server/index.js.
2. Add label UI in dashboard.
3. Refactor MODELE_IA.js into quality + features + rules + policy.
4. Export a dataset.
5. Train Random Forest / XGBoost baseline.
6. Connect Python FastAPI inference.
7. Display confidence, abstain, and recommendation reason.

This gives a real intelligent model pipeline while staying practical for your current ESP32 hardware and dashboard.
